## 3. Gate 5A — Backup และการตรวจ Backup

ทดสอบกับสำเนาข้อมูลจริง (dump ของทีม กู้ลง PostgreSQL 16 ในเครื่องทดสอบ ฐาน `vora_mig`)

| กรณี | ผล |
|---|---|
| ไฟล์สำรองปกติ | ผ่าน: 19 ตาราง 653 แถว ตรงทุกตาราง (audit_log 21 · chat_sessions 48 · eval_cases 20 · eval_runs 0 · feedback 6 · intent_examples 326 · knowledge 15 · messages 134 · model_versions 2 · news 4 · patrol_routes 1 · programs 7 · schedules 4 · settings 0 · system_events 43 · unanswered 2 · users 2 · vision_classes 6 · vision_samples 12) |
| ไฟล์ตัดเหลือ 20 KB | หยุด: "อ่านสารบัญไฟล์สำรองไม่ได้ … end of file" |
| ไฟล์ถูกแก้ไบต์กลางไฟล์ | หยุด: "กู้ข้อมูลจากไฟล์สำรองไม่สำเร็จ … could not uncompress data" (สารบัญยังอ่านได้ — การกู้แบบสตรีมจับได้) |
| ไฟล์ว่าง | หยุด: "ไม่พบไฟล์สำรองหรือไฟล์ว่าง" |
| ฐานข้อมูลมีแถวเพิ่มหลังสำรอง | หยุด: "ตาราง feedback: ไฟล์สำรอง 6 แถว แต่ฐานข้อมูล 7 แถว" |
| SQLite ดี / เสีย | ผ่าน 19 ตาราง 482 แถว / หยุด "database disk image is malformed" |
| พาธมีภาษาไทย ช่องว่าง `#` `?` | ผ่าน (ใช้ `Path.as_uri()`) |

วิธีตรวจ: `pg_restore --list` (สารบัญ + มี TABLE DATA ครบทุกตาราง) → `pg_restore --data-only -f -` กู้แบบสตรีมออกเป็นข้อความ **ไม่เขียนลงฐานข้อมูลใด** นับแถว COPY ทีละตาราง เทียบกับ `SELECT COUNT(*)` · บันทึก SHA-256 + ผลใน `<ไฟล์>.verify.json`

## 4. Gate 5B — Migration

**บนสำเนาข้อมูลจริง (PostgreSQL 16):**

| ขั้น | ผล |
|---|---|
| `status` | `0001 ยังไม่ทำ` |
| `upgrade` | สำรอง → ตรวจผ่าน 19 ตาราง 653 แถว → ALTER 3 คอลัมน์ในทรานแซกชันเดียว → **md5 + จำนวนแถวทุกตารางตรงกับก่อนทำ** · ใช้เวลา 0.9 วิ (รวมสำรอง+ตรวจ) |
| ตรวจคอลัมน์ | `location` varchar 255 / `location_type` 16 / `location_map_url` 500 · nullable YES · ไม่มี default · ข่าวเดิม 4 รายการเป็น NULL ทั้งหมด |
| `upgrade` ซ้ำ | "ฐานข้อมูลเป็นรุ่นล่าสุดแล้ว" ไม่สำรองซ้ำ ไม่แก้อะไร |
| `downgrade 0001` ตอบ `no` | ยกเลิก ไม่แก้อะไร |
| `downgrade 0001` ตอบ `YES` (หลังใส่สถานที่ 1 ข่าว) | สำรอง+ตรวจ → ส่งออก `news-0001-export-*.json` (1 รายการ หอประชุม/campus) → ลบคอลัมน์ → **ข้อมูลทั้ง 19 ตารางตรงกับต้นฉบับ** และ `pg_dump -s` เหมือนต้นฉบับทุกบรรทัด (ต่างเฉพาะ token สุ่มของ pg_dump) |
| เซิร์ฟเวอร์เปิดอยู่ | upgrade/downgrade หยุด: "เซิร์ฟเวอร์ VORA ยังทำงานอยู่ — ปิดหน้าต่าง start.bat ก่อน" |
| เปิดเซิร์ฟเวอร์ด้วยโค้ดใหม่ก่อน upgrade | หยุดเริ่มระบบ: "ฐานข้อมูลยังเป็นโครงสร้างรุ่นเก่า (ขาดคอลัมน์ news: …) — ปิด start.bat แล้วรัน migrate.bat upgrade ก่อน" · ฐานข้อมูลไม่ถูกแก้ (status ยัง "ยังไม่ทำ") |
| ซ้อมขั้นตอนจริงตั้งแต่ต้นด้วยโค้ดสุดท้าย | ตัวกันหยุด → status → upgrade → เปิดเซิร์ฟเวอร์ได้ · `/api/news` 4 ข่าว ฟิลด์เดิมครบ สถานที่ null · `/api/timeline` 4 รายการ เวลา "ไม่ระบุ" ทั้งหมด · ลายนิ้วมือหลัง upgrade = ต้นฉบับทุกตาราง |

หมายเหตุ: หลังเปิดเซิร์ฟเวอร์ ตาราง `system_events` จะมีแถวเพิ่มตามปกติ (บันทึก "VORA started") — ไม่ใช่ผลของ Migration

**pytest `test_migration_0001.py` (SQLite) 9 กรณี:** ตัวกันหยุดโดยไม่แก้ฐานข้อมูล · upgrade เพิ่มคอลัมน์ NULL ได้และข้อมูลเดิมไม่เปลี่ยน + มีไฟล์สำรอง + บันทึก log · ทำซ้ำได้ · downgrade ส่งออกและคืนโครงสร้างเดิม · downgrade ต้องพิมพ์ YES · โครงสร้างทำไปบางส่วน → หยุด · ไฟล์สำรองเสีย → หยุดก่อนแก้ · เซิร์ฟเวอร์เปิดอยู่ → หยุด · ตรวจพบจำนวนแถวไม่ตรง

## 5. Gate 5C — หลังบ้านและ API

- ฟอร์มข่าว: **ประเภทสถานที่** (ไม่ระบุ / ภายในวิทยาลัย / ภายนอกวิทยาลัย / ออนไลน์) · **ชื่อสถานที่** (จำเป็นเฉพาะภายใน/ภายนอก) · **ลิงก์แผนที่** (ปิดเมื่อออนไลน์/ไม่ระบุ) · คำแนะนำช่องวันจัด "ถ้าไม่ทราบเวลา ให้ตั้งเวลา 00:00 ระบบจะแสดงเฉพาะวันที่" · ตารางข่าวมีคอลัมน์ "วันจัด / สถานที่"
- API ตรวจซ้ำทุกครั้ง (ไม่พึ่งหน้าเว็บ): ประเภทผิด · มีชื่อแต่ไม่เลือกประเภท · ภายใน/ภายนอกไม่มีชื่อ · ออนไลน์มีลิงก์แผนที่ · ลิงก์ไม่ใช่ `https://` (รวม `http://`, `javascript:`) · ชื่อเกิน 255 → 400 พร้อมข้อความไทย และ **ไม่แก้ข้อมูลใด ๆ**
- **ไม่ส่งฟิลด์สถานที่ = ไม่แก้ค่าเดิม** (หน้าหลังบ้าน/สคริปต์รุ่นเก่าแก้ข่าวแล้วสถานที่ไม่หาย) · ข้อความว่าง = NULL · ตัดช่องว่าง
- การเปลี่ยนสถานที่ถูกบันทึกใน `audit_log` · กติกาเดิม "editor แก้ข่าวที่เผยแพร่แล้ว → รออนุมัติ" ยังทำงาน
- `/api/news`, `/api/news/{id}`: ฟิลด์เดิมครบ + `location`, `location_type`, `location_map_url`
