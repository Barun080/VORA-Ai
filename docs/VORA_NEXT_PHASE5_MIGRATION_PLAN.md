## 2. การเปลี่ยนแปลงฐานข้อมูล (ตาราง `news` ตารางเดียว)

| คอลัมน์ใหม่ | ชนิด | ค่าว่าง | ความหมาย |
|---|---|---|---|
| `location` | `VARCHAR(255)` | **NULL ได้** | ชื่อสถานที่ตามที่เจ้าหน้าที่กรอก เช่น "หอประชุม อาคาร 1 ชั้น 2" หรือ "ศูนย์ประชุมแห่งชาติสิริกิติ์ ห้อง 3" |
| `location_type` | `VARCHAR(16)` | **NULL ได้** | `campus` = ภายในวิทยาลัย · `external` = ภายนอก · `online` = ออนไลน์ · NULL = ไม่ระบุ |
| `location_map_url` | `VARCHAR(500)` | **NULL ได้** | ลิงก์แผนที่ (ไม่บังคับ — สำหรับภายใน/ภายนอก ใช้ทำ QR นำทาง) รับเฉพาะ `https://` · **ไม่ใช้กับกิจกรรมออนไลน์** |

**กติกาตามประเภท (ตรวจที่ API หลังบ้าน):**

| ประเภท | ชื่อสถานที่ (`location`) | ลิงก์แผนที่ |
|---|---|---|
| ไม่ระบุ (NULL) | ต้องว่าง (กรอกชื่อแล้วต้องเลือกประเภท) | ต้องว่าง |
| ภายในวิทยาลัย `campus` | **จำเป็น** | ไม่บังคับ (`https://`) |
| ภายนอก `external` | **จำเป็น** | ไม่บังคับ (`https://`) |
| ออนไลน์ `online` | **ไม่บังคับ** (เช่น "Facebook Live เพจวิทยาลัย") | **ไม่รับ** |

- ไม่มีค่าเริ่มต้น ไม่มี NOT NULL ไม่มี Index ใหม่ → PostgreSQL เพิ่มคอลัมน์แบบแก้ Metadata อย่างเดียว ไม่เขียนข้อมูลทั้งตารางใหม่
- **ไม่แก้/ไม่ลบข้อมูลเดิมแม้แต่แถวเดียว** · ตารางอื่นไม่เปลี่ยน
- **D1 อนุมัติ 3 คอลัมน์** + ประเภท `online`

## 3. Backup + ตรวจความสมบูรณ์ (ก่อน Migration ทุกครั้ง — อัตโนมัติใน `migrate.bat`)

1. `pg_dump -Fc` (ใช้ `backup_db.py` เดิม) → `_backups/database/vora-<เวลา>-before-0001-news-location.dump` (ไม่เขียนทับไฟล์เดิม)
2. **ตรวจไฟล์ (`scripts/verify_backup.py` ใหม่):** `pg_restore --list` อ่านสารบัญได้ → `pg_restore -f -` คลายข้อมูลทุกไบต์ (พิสูจน์ว่าไฟล์ไม่เสีย) → นับแถวทุกตารางในไฟล์สำรอง เทียบกับฐานข้อมูลจริงขณะนั้น ต้องตรงกันทุกตาราง → บันทึก SHA-256 ของไฟล์
3. ไม่ผ่านข้อใดข้อหนึ่ง = **หยุด ไม่ Migrate**
4. กู้คืน (ถ้าจำเป็น): `backup_db.bat --restore <ไฟล์>` เดิม

## 4. Migration

### 4.1 สคริปต์ `scripts/migrate_schema.py` (ใหม่) + `migrate.bat`
```
migrate.bat status              ดูว่า Migration ไหนทำแล้ว/ยังไม่ทำ (อ่านอย่างเดียว)
migrate.bat upgrade             Backup → ตรวจ Backup → เพิ่มคอลัมน์ → ตรวจผล
migrate.bat downgrade --confirm Backup → ส่งออกข้อมูลสถานที่เป็นไฟล์ → ลบ 3 คอลัมน์ → ตรวจผล
```
- Migration `0001_news_location` มีทั้ง `upgrade()` และ `downgrade()` ใช้ได้ทั้ง PostgreSQL และ SQLite
- **ตรวจสถานะจากโครงสร้างจริง** (คอลัมน์มีอยู่หรือไม่) → รันซ้ำได้ปลอดภัย (Idempotent) ไม่ต้องสร้างตารางติดตามเวอร์ชันเพิ่ม
- ทำใน Transaction เดียว (PostgreSQL) ล้มกลางทาง = ย้อนกลับทั้งหมด
- ตรวจหลังทำ: md5 ของข้อมูลข่าวเดิม + จำนวนแถวทุกตาราง ต้องเท่าก่อนทำ · ไม่เท่า = Rollback และรายงาน

### 4.2 Downgrade
- ต้องใส่ `--confirm` · ทำ Backup ใหม่ก่อน · **ส่งออกข้อมูลสถานที่ทุกแถวที่ไม่ว่างเป็นไฟล์** `_backups/database/news-location-export-<เวลา>.json` ก่อนลบคอลัมน์ (การลบคอลัมน์ทำให้ข้อมูลสถานที่ที่กรอกหลัง Upgrade หายจากตาราง — ไฟล์ส่งออกนี้คือทางนำกลับ)
- โค้ดของ Phase 5 ต้องย้อนกลับพร้อมกัน (ไฟล์ใน `before-changes`)

### 4.3 ติดตั้งใหม่ (ฐานข้อมูลว่าง)
`create_all` สร้างคอลัมน์ให้ครบเอง → `migrate.bat status` รายงานว่าทำแล้ว

### 4.4 ตัวกันเมื่อโค้ดใหม่เปิดก่อน Migrate
ตอนเปิดเซิร์ฟเวอร์ ถ้าพบว่า `news` ยังไม่มีคอลัมน์ใหม่ → **หยุดพร้อมข้อความภาษาไทยชัดเจน** ("ต้องรัน migrate.bat upgrade ก่อน") แทนการเปิดแล้วล้มทุกคำขอข่าว · ไม่ Migrate เองอัตโนมัติ (ให้ทีมควบคุมจังหวะ Backup)

### 4.5 กันการล้างข้อมูลสถานที่จากหน้าหลังบ้านรุ่นเก่า
`PUT /api/admin/news/{id}`: ฟิลด์สถานที่จะถูกแก้ **เฉพาะเมื่อคำขอส่งฟิลด์นั้นมา** (ไม่ส่ง = คงค่าเดิม) · ฟิลด์เดิมทำงานเหมือนเดิมทุกอย่าง · การแก้สถานที่ถูกบันทึกใน Audit Log เหมือนฟิลด์อื่น

## 5. หลังบ้าน (Admin)
- ฟอร์มข่าว: **ประเภทสถานที่** (ไม่ระบุ / ภายในวิทยาลัย / ภายนอกวิทยาลัย / ออนไลน์) · **ชื่อสถานที่** · **ลิงก์แผนที่** (ไม่บังคับ ไม่ใช้กับออนไลน์) · คำแนะนำช่องวันจัดกิจกรรม: "ถ้าไม่ทราบเวลา ให้ตั้งเวลาเป็น 00:00 ระบบจะแสดงเฉพาะวันที่"
- ตรวจข้อมูลตามตารางกติกาข้อ 2 · ตัดช่องว่างหัวท้าย · ข้อความว่าง = NULL
- ตารางรายการข่าว: เพิ่มคอลัมน์ "วัน-เวลา-สถานที่" ให้เห็นข่าวที่ยังไม่มีสถานที่
- สิทธิ์เดิมไม่เปลี่ยน (editor แก้ได้ แก้ข่าวที่เผยแพร่แล้ว → กลับไปรออนุมัติเหมือนเดิม)

## 6. Time Portal
- `GET /api/timeline` (ใหม่ อ่านอย่างเดียว) เฉพาะข่าวที่เผยแพร่และอยู่ในช่วงเผยแพร่ (เงื่อนไขเดียวกับ `/api/news`)
- แบ่งกลุ่มตามเวลา **Asia/Bangkok (UTC+7 คงที่ ไม่มีเวลาออมแสง — ไม่ขึ้นกับ timezone ของเครื่องหรือแพ็กเกจ tzdata)**: **ที่ผ่านมา** · **วันนี้** · **ที่จะมาถึง** · **วันสำคัญ** · ข่าวที่ **ไม่มี `event_date` ไม่ถูกจัดเป็นวันนี้/ที่จะมาถึง/วันสำคัญ** (อยู่กลุ่ม "ไม่ระบุวันที่")
- **เวลา (D2):** `event_date` เวลา 00:00 = "ไม่ระบุเวลา" แสดงเฉพาะวันที่ · **ไม่แก้เวลาของข้อมูลเดิมในฐานข้อมูล** (ตีความตอนแสดงผลเท่านั้น)
- **วันสำคัญ (D3 ฉบับปรับ):** เฉพาะข่าวประเภท **รับสมัคร (`admission`)** ที่ **เผยแพร่แล้ว** และ **อยู่ในช่วงเผยแพร่** (`publish_at` ≤ ตอนนี้ และ `expire_at` ว่างหรือ > ตอนนี้ — ตรวจทุกคำขอ) และ **มี `event_date` จริง อยู่ระหว่างวันนี้ถึง 60 วันข้างหน้า** · **ความสำคัญ (priority) ไม่ใช้ตัดสินวันสำคัญ** · แสดงเฉพาะวันที่ที่มีในฐานข้อมูล ไม่สร้างกำหนดการ
- แต่ละรายการ: วันที่ · เวลา · **สถานที่ตามที่เจ้าหน้าที่กรอก หรือ "ไม่ระบุสถานที่"** (ไม่อนุมานจากเนื้อหาข่าว) · ป้ายภายใน/ภายนอก · ภาพ · รายละเอียด · อวตารบรรยาย (พูดสถานที่เฉพาะเมื่อมีข้อมูล) · QR ดูต่อบนมือถือ (`/m/?news=<id>`) และ QR แผนที่ (ถ้ามีลิงก์)
- `/api/news`, `/api/news/{id}` เพิ่มฟิลด์ `location`, `location_type`, `location_map_url` (เพิ่มอย่างเดียว ฟิลด์เดิมไม่เปลี่ยน) · หน้ามือถือแสดงวัน-เวลา-สถานที่
- เข้าใช้จาก: หมวด "ข่าวสาร" ใน Orbital Menu (ปุ่ม "ไทม์ไลน์กิจกรรม") และเมนูตัวอักษรใหญ่

## 11. ลำดับการทำงานจริง (ตาม Gate 5A → 5E)

| ขั้น | ที่ไหน | งาน |
|---|---|---|
| 5A | เครื่องทดสอบ (สำเนาข้อมูลจริงบน PostgreSQL 16) | เขียน/ทดสอบ `verify_backup.py` + ขั้น Backup ของ `migrate_schema.py` กับสำเนาข้อมูลจริง (รวมกรณีไฟล์เสีย/จำนวนแถวไม่ตรง ต้องหยุด) |
| 5B | เครื่องทดสอบ | Migration 0001 upgrade/downgrade/status บนสำเนาข้อมูลจริง (PostgreSQL) + SQLite · ตัวกันตอนเปิดเซิร์ฟเวอร์ · pytest |
| 5C | เครื่องทดสอบ | Admin + API (ข้อ 5) · pytest |
| 5D | เครื่องทดสอบ | Time Portal (ข้อ 6) · pytest + ชุดทดสอบเบราว์เซอร์ Gate 5D |
| 5E | เครื่องทดสอบ | Regression ทั้งหมด |
| ติดตั้ง | เครื่องของทีม | Claude ตรวจไฟล์เดิมเทียบ Backup → สำรองไฟล์ → เขียนไฟล์ (ไม่แตะฐานข้อมูล) |
| 5A/5B จริง | เครื่องของทีม | ทีมปิด `start.bat` → `migrate.bat upgrade` (Backup → ตรวจ Backup → Migrate → ตรวจผล) → ส่งผลให้ตรวจ |
| 5E จริง | เครื่องของทีม | เปิด `start.bat` → `test.bat` บน PostgreSQL → ส่งผลให้ตรวจ |

เหตุผลที่ติดตั้งหลังผ่านครบทุก Gate บนเครื่องทดสอบ: ทีมจะได้รัน Migration ครั้งเดียวพร้อมโค้ดที่ทดสอบครบแล้ว ไม่ต้องติดตั้ง 2 รอบ · ระหว่างเขียนไฟล์ เซิร์ฟเวอร์ที่เปิดอยู่ใช้โค้ดเดิมในหน่วยความจำ ถ้าเซิร์ฟเวอร์ถูกรีสตาร์ทก่อน Migrate ตัวกันข้อ 4.4 จะหยุดพร้อมบอกให้รัน `migrate.bat upgrade` (ไม่มีข้อมูลเสียหาย)

**หยุดและรายงานทันทีถ้า:** Backup ไม่ผ่านการตรวจ · ข้อมูลเดิมเปลี่ยน (md5/จำนวนแถว) · พบข้อมูลเดิมที่ขัดกับกติกาใหม่ · Migration ล้มกลางทาง
